# 智能科技微前端迁移修正说明

> 适用代码基线：`dev-zhike`，2026-08-28。
> 本文记录智能科技驾驶舱迁入 `apps/smart-technology` 后的**问题修正**过程，不替代产品验收记录。
> 前置阅读：[业务域微前端开发指南](./业务域微前端开发指南.md)、[地产微前端迁移开发说明](./地产微前端迁移开发说明.md)。
> 主体迁移代码见提交 `692735d74`，本文对应的修正散落在该提交及其后的工作区改动。

---

## 1. 背景：为什么需要这轮修正

智能科技首轮迁移套用了其它五个业务域通用的 `DOMAIN_PAGES` 空壳脚手架（tuju / ruida / ziyunying / commercial-vehicle / commercial-society）。但那套脚手架有一个隐含假设：

> **一个业务域 = 一组平级的三级页，每页一条 path。**

智能科技不满足这个假设。它是**两级导航 + 左侧三/四级菜单**的四层结构：

```text
一级：板块 / MINI卡 / 专用车 / 007 / 瑞弗 / 瑞源 / 绿能 / 农机
      ← SMART_TECH_FIRST_LEVEL_TABS，components/ThreeMenu 渲染
  └─ 二级：总览 / 运营 / 财务 / 营销 / 生产 / 质量 / 人力 / 数字化
        ← SMART_TECH_SECOND_LEVEL_TABS，components/common/SecondNav.vue 渲染
      └─ 三级：项目地图 / 经营矩阵 / 线索 / 新媒体 …   ← ids
            └─ 四级：项目全景 / 全景明细 / 总览 …      ← currId
                  ← LeftMenu（propertyGraticules/mettingAnalysisNew）渲染
```

套脚手架时把**一级和二级压成了一层**：`DomainEntry.vue` 用 `@cockpit/kit/ui` 的 `ThreeLevelNavigationBar` 渲染 `DOMAIN_PAGES`，而 `DOMAIN_PAGES` 里装的是本该属于**二级**的 8 个板块。这一个决策连锁引发了后续全部问题。

---

## 2. 核心结论：URL 契约是不可动的地基

智能科技迁移最重要的一条结论：

> **旧的 query 契约（单一 path + 四层 query）是全局事实来源，不能改为按板块拆 path。**

因为有五处已迁移代码在直接读它，它们不在导航层，改导航层不会同步：

| 位置 | 依赖的 query |
| --- | --- |
| `components/common/BreadcumbTabs.vue:79` | `route.query.activeTabKey !== 'zhike'` 直接决定页签标题是否渲染 |
| `components/common/BreadcumbTabs.vue:76` | 独立页标题按 `route.query.indexActiveTab` 取 |
| `components/projectMap/Breadcumb.vue` | 下钻返回时 `router.replace` 回写完整四层 query |
| `shared/cockpit/page-title.ts` | `resolveSmartTechnologyPageSegments` 按四层 query 自顶向下拼页面名 |
| `components/clueFunnel/BizDashboard.vue:135` | 对外分享链接是完整四层 query 深链 |

宿主侧 `src/layouts/page/cockpitShell/navigation-path.ts` 的 `getSmartTechnologyDefaultPath()` 也生成 `?activeTabKey=…&indexActiveTab=…`，与该契约天然一致。

标准 URL 形态（宿主）：

```text
/konggu-jww/smartTechnology?currId=23_1&ids=23&activeTabKey=zhike&indexActiveTab=operation
```

**子应用内只有一条路由 `path: '/'`**，层级全部由 query 表达。桥接负责补/去宿主前缀，query 原样透传。

## 3. 五项修正

### 3.1 恢复两级导航（SecondNav 丢失）

**现象**：二级导航条整个消失，一级导航（板块 / MINI卡 …）连同 `ThreeMenu` 右侧的 `expandedTitle` 展开按钮也不见了。

**原因**：二级板块被顶到 `DomainEntry` 的一级导航条上，`businessPage/zhike.vue` 里的 `<second-nav>` 整块被删（`SecondNav` import、`handleTabChange`、`closeOrOpen` 一并移除）。

**处置**——采用「页面自己拥有两级导航」，不扩展 kit 组件：

- `DomainEntry.vue` 退化为**纯外壳**：只保留缩放容器、无权限空态、独立模式撑满视口，不再渲染任何导航条。
- `views/kongguJww/smartTechnology/index.vue` 成为唯一页面组件，用微应用自带的 `components/ThreeMenu` 渲染一级导航。该目录与主应用版 `diff` 完全一致（含 `treeIcon.png` 等 assets）。
- `businessPage/zhike.vue` 还原 `<second-nav>` 及 `handleTabChange`（含 `leftMenuCache` 还原三/四级、清理 `projectMapFilter` / `zkDownList`）。

> **为什么不扩展 kit 的 `ThreeLevelNavigationBar`**：它被另外六个子应用共用，加 `isExpanded` / `expandedTitle` 会把智能科技的特有形态推给所有业务域。微应用已自带功能等价的 `ThreeMenu`，直接用。

**校验基线**：`zhike.vue` 与 `leftMenu/index.vue` 现在与主应用版**逐字节相同**，可用 `diff` 持续守护：

```bash
diff src/views/kongguJww/smartTechnology/businessPage/zhike.vue \
     apps/smart-technology/src/views/kongguJww/smartTechnology/businessPage/zhike.vue
diff src/views/kongguJww/propertyGraticules/mettingAnalysisNew/components/leftMenu/index.vue \
     apps/smart-technology/src/views/kongguJww/propertyGraticules/mettingAnalysisNew/components/leftMenu/index.vue
```

### 3.2 路由收敛为单条（URL 形态不一致）

**现象**：切二级板块时 URL 的 **path** 在变（`/overview`、`/operation`…），而旧页面是单一 path 只变 query。

**原因**：脚手架给每个二级板块发了独立 path，并新增 `businessPage/routeMap.ts` 做 path ↔ 旧二级 key 映射。

**处置**：

| 文件 | 改动 |
| --- | --- |
| `src/config/smartTechnology.ts` | `DOMAIN_PAGES` 8 条 → 1 条：`key: 'cockpit'`、`path: '/'`、`hostPath: '/konggu-jww/smartTechnology'` |
| `src/router.ts` | 空路径直接挂页面，**移除 `{ path: '', redirect: getDefaultPath() }`** —— 否则 `'/'` 自我重定向 |
| `src/router/bridge.ts` | 删除 `resolveEntryTarget` / `hasEntryHint`，改为原样透传 |
| `businessPage/routeMap.ts` | 删除 |
| `views/smartTechnology/SmartTechnologyCockpit.vue` | 删除（职责被 `index.vue` 吸收） |
| `apps/check-domain-scaffolds.mjs` | `pages: 8` → `1` |

**连带修复**：`BreadcumbTabs` 的 `activeTabKey !== 'zhike'` 恒为真，页签标题在收敛前**已全部失效**；收敛后自动恢复。埋点 `pageId` 由 `hostPath + query` 拼出，也自动回到旧口径（已验证输出 `#/konggu-jww/smartTechnology?activeTabKey=zhike&indexActiveTab=sales&ids=21&currId=21_1`）。

**两个易踩的坑**：

1. **`permission` 不能用 `dexis:smartTechnology:zhike`**。一、二级板块可见性由页面内 `isZhikeTabs` / `getTabPanes` 判断，其中兼容了「只配二级权限、未配 `zhike`」的历史账号。若在路由层按 `zhike` 卡死，这些账号会被守卫直接挡在 `/unauthorized`。改用业务域入口标识 `dexis:technology:query`（与宿主二级导航「智能科技」的 `auth` 一致）。
2. **`permission` 必须写字面量**。`apps/check-domain-scaffolds.mjs` 用正则 `/permission:\s*'/g` **按字面量计数**校验条数，引用 `DOMAIN_METADATA.entryPermission` 会让计数变 0。同理，注释里也不要出现 `permission: '` 这样的字样，否则会被多计一条。

### 3.3 `DOMAIN_PERMISSION_CODES` 覆盖菜单树全部层级

路由收敛后不能再从 `DOMAIN_PAGES` 推导独立开发（`?mock=1`）所需的权限全集。改为汇总：

```ts
export const DOMAIN_PERMISSION_CODES = [
  DOMAIN_METADATA.entryPermission,
  ...DOMAIN_PAGES.map((page) => page.permission),
  ...SMART_TECH_FIRST_LEVEL_TABS.map((tab) => tab.auth),   // 一级
  ...SMART_TECH_SECOND_LEVEL_TABS.map((tab) => tab.auth),  // 二级
  ...Object.values(SMART_TECH_MENU_TREE).flatMap((nodes) => nodes.map((t) => t.auth)), // 三级
  ...Object.values(SMART_TECH_CURR_ID_AUTH),               // 四级
].filter((code, index, codes) => codes.indexOf(code) === index);
```

**三级 auth 极易漏**。`menuList` 是按**三级 auth**（如 `dexis:smartTechnology:operation:manager`）过滤的，缺一个就会让该三级节点消失；若当前 `thirdId` 正好指向它，`zhike.vue` 的 `isAuth` 转为 `false`，**整个 `.smart-container` 连同 LeftMenu 都不渲染**，点击毫无反应。定位时容易误判成路由问题。

> 该结论是排查中用 vitest + jsdom 挂载真实 `zhike.vue` 得到的：漏掉 `:operation:manager` 时 `.left-menu` / `.smart-container` 均为 `false`，补上后立即恢复。

### 3.4 Platform → 旧 inject 契约桥接（引用抖动）

**现象**：左侧菜单点击后选中态立刻被覆盖、面包屑不联动，连点多次后宿主显示「子应用暂时无法加载」。

**原因**——宿主两个适配器的订阅粒度都比语义更粗：

| 适配器 | 底层实现 | 实际触发时机 |
| --- | --- | --- |
| `auth.onAuthChange` | `userStore.$subscribe` | **任何** user store 变更（token 刷新、埋点写入…），且 `getPermissions()` 每次返回**新数组** |
| `fullscreen.onChange` | `fullscreenStore.$subscribe` | 该 store 里还有 `cachedMenuFlag`（左侧菜单收起按钮会写），**任何字段**变更都回调 |

若无条件 `menus.value = platform.auth.getPermissions()`，引用每次都变，连锁：

```text
menus 新引用 → zhike.vue 的 tabs / menuList 重算
            → LeftMenu 的 watch(() => props.menuList, { deep: true }) 重置 localMenuList
            → isChoose / showChild 选中态全部抹掉
            → 点击不切页、面包屑不联动；反复触发把子应用推进 error 态
```

「推进 error 态」的机制：`bootstrap/createAppRuntime.ts` 里 `app.config.errorHandler` 与 `unhandledrejection` 都会调 `platform.lifecycle.error()`，宿主 `MicroAppContainer` 据此切到 error 面板 —— 所以**任何**子应用内的 Vue 错误都会表现为「子应用暂时无法加载」。

**处置**：赋值前做内容比对，只在真的变化时更新引用。`index.vue` 与 `DomainEntry.vue` 两处都要改；`fullscreen` 回调同样加值比对，避免 `setFullscreen` 回写环。

```ts
function syncPermissions() {
  const next = platform.auth.getPermissions();
  const prev = menus.value;
  if (next.length === prev.length && next.every((code, i) => code === prev[i])) return;
  menus.value = next;
}
```

**通用建议**：任何业务域从 `platform.auth.onAuthChange` / `platform.fullscreen.onChange` 同步状态时，都应做内容比对再赋值 —— 这两个回调的触发频率远高于其语义。

### 3.5 权限就绪时序（首帧被钉在 `/unauthorized`）

**现象**：SecondNav 要点两次才跳；有 LeftMenu 时压根不跳、路由不变。

**原因**：嵌入模式下宿主 `adapters/auth.ts` 的 `ready()` 是 `Promise.resolve()`，**不等权限就位**。而 `createAppRuntime` 在 `await platform.auth.ready()` 后立刻建路由，此时 `getPermissions()` 常为空数组 → 守卫判定无权限 → 重定向 `/unauthorized`，且**之后权限到位没有任何逻辑把它导回来**。

于是第一次点击只是把路由从 `/unauthorized` 挪回业务路由（所以要点两次）；LeftMenu 更糟 —— 它拼的是 `${route.path}?currId=…`，此时 `route.path` 是 `/unauthorized`，拼出的路径再次被守卫打回，永远不跳。

> 这是脚手架原有的时序漏洞，被路由收敛**放大成必现**：收敛前 `getDefaultPath()` 有 8 个候选页，收敛后只剩一条，一旦它鉴权失败就必然落到 `/unauthorized`。

**处置**：区分「权限尚未就绪」与「确实无权限」。

```ts
// src/router.ts
const isPermissionReady = () =>
  platform.auth.isAdmin() || platform.auth.getPermissions().length > 0;

router.beforeEach((to) => {
  if (!isPermissionReady()) return true;   // 未就绪时放行，不鉴权
  /* …原有鉴权… */
});
// catch-all 同样回落到 '/' 而非 /unauthorized
{ path: '/:pathMatch(.*)*', redirect: () => (isPermissionReady() ? getDefaultPath() : '/') }
```

`DomainEntry.vue` 补兜底：若确实落在 `/unauthorized` 而权限随后到位，主动 `replace` 回业务路由并保留 query。

**注意不要为修 bug 放水鉴权**：`isPermissionReady()` 只在权限集合**为空**时放行；真正拿到权限但无本域权限的账号仍会正确落到 `/unauthorized`（已验证）。

### 3.6 页签过滤前缀（面包屑恒为空）

**现象**：首次进入面包屑不初始化，点 SecondNav 也加不出页签。

**原因**：`store/modules/engineering.ts` 的 `smartTechnologyStore.setTabItems` 从主应用整份拷来，按**宿主**前缀过滤：

```ts
tabItems.filter((item) => item.key.startsWith('/konggu-jww/smartTechnology'))
```

而 `BreadcumbTabs.vue:104` 存的 `key` 是 `route.fullPath`。主应用里是 `/konggu-jww/smartTechnology?…`（命中）；子应用里是 `/?activeTabKey=zhike&…`（**一条都不命中**）→ `tabItems` 恒为空 → 外层 `v-if="tabItems.length > 0"` 永不渲染。

**处置**：改为校验「子路由绝对路径」，并剔除宿主格式的历史残留（`sessionStorage` 与宿主同源共享，切换 MFE 开关后可能留下旧格式 key，这类 key 在子应用 Router 里解析不出来）：

```ts
const items = tabItems.filter(
  (item) =>
    typeof item?.key === 'string' &&
    item.key.startsWith('/') &&
    !item.key.startsWith('/konggu-jww'),
);
```

## 4. 桥接：宿主陈旧快照倒灌（重点）

这是本轮最隐蔽的一个问题，**症状与「路由不生效」高度相似但成因完全不同**，值得所有业务域参考。

### 4.1 现象与证据

点左侧菜单，页面闪一下又弹回原页；路由看似没变。浏览器日志（临时埋点）：

```text
[LM-DIAG] push (leaf)  /?currId=23_2&ids=23&...        ← 点「全景明细」
[ZK-DIAG] currId: '23_2'                                ← 子应用确实切过去了
[BR-DIAG] host->child  hostGave → '/?currId=23_1&...'   ← 宿主回灌了旧的 23_1
                       childCurrent = '...23_2...'
                       willSkip: false                  ← 未跳过，执行覆盖
[BR-DIAG] child afterEach '...23_1...' syncing:true     ← 子应用被改回去
[ZK-DIAG] currId: '23_1'                                ← 弹回原页
```

### 4.2 成因

1. 子应用 `afterEach` 里用 `void platform.router.navigate(...)` 推给宿主 —— **不 await**，异步排队。
2. 宿主导航落地前仍停在旧 URL。而宿主 `adapters/router.ts` 的 `onRouteChange` 挂在宿主 router 的**每一次** `afterEach` 上，回调里给的是 `currentLocation()` —— 也就是「宿主当下」的**旧快照**。
3. 桥接拿到旧快照，与子应用当前不一致 → `router.replace(旧值)` → 把刚切好的新路由覆盖掉。

SecondNav「点两次」同源：第一次被旧快照打回，第二次宿主已追平才生效。

### 4.3 处置

在 `bridge.ts` 记录子应用最后一次主动推给宿主的目标，宿主回灌与之不一致时一律忽略，直到宿主确实追平：

```ts
let pendingHostTarget: string | null = null;

platform.router.onRouteChange(async (location) => {
  const resolved = router.resolve(toRouterRoute(location));
  if (!resolved.matched.length) return;

  if (pendingHostTarget !== null) {
    if (resolved.fullPath === pendingHostTarget) {
      pendingHostTarget = null;   // 宿主已追平，握手完成
      return;
    }
    return;                       // 宿主还停在旧快照上：忽略
  }
  /* …宿主侧主动导航，照常同步… */
});

router.afterEach((to) => {
  if (syncingFromPlatform || platform.mode !== 'embedded') return;
  pendingHostTarget = to.fullPath;
  void platform.router.navigate(toPlatformRoute(to));
});
```

宿主侧主动发起的导航（无 pending）仍照常同步，不影响外部深链与宿主菜单跳转。

### 4.4 ⚠️ 该修复的验证状态

**此修复未能在自动化测试中验证。** 我们写了双向桥接的复现用例，但无论加不加修复都得到正确结果 —— 测试 harness 没能复刻出浏览器里的并发时序，因此它既没复现 bug、也无法证明修复有效。

修复逻辑直接针对日志中「旧快照覆盖新状态」这一确凿现象设计，但**最终判断依赖真实浏览器验证**。后续若该现象复现，建议：

1. 重新加回 `[BR-DIAG]` 埋点（见下节方法），确认是否仍是旧快照倒灌；
2. 若是，考虑更强的方案 —— 参考地产桥的 `platformNavigationQueue`（串行提交）+ `outboundPlatformTarget`（标记自身写入），把 fire-and-forget 改为串行 await。

## 5. 排查方法：三点埋点法

本轮定位的有效手段。纯代码推断在双向桥接 + 四层 query 的场景下效率很低，建议直接埋点。

在三个决策点各插一条日志，一次点击即可唯一定位卡点：

| 埋点 | 位置 | 输出 |
| --- | --- | --- |
| `[LM-DIAG]` | `leftMenu/index.vue` 的 `handleClick` | 是否触发、`willEarlyReturn`、拼出的 routePath、`push` 是否 reject |
| `[BR-DIAG]` | `bridge.ts` 两个方向的回调 | `hostGave` / `childCurrent` / `willSkip` |
| `[ZK-DIAG]` | `zhike.vue` 的 `isAuth` 之后 | `currId` / `thirdId` / `activeTab` / `isAuth` / `menuIds` |

判读表：

| 日志表现 | 结论 |
| --- | --- |
| 无 `[LM-DIAG] click` | 点击未进 `handleClick`（事件层） |
| `willEarlyReturn: true` | 命中「收起」分支，只折叠不跳转 |
| `push FAILED` | 导航被守卫中断，错误对象给出原因 |
| push 成功但 `[ZK-DIAG]` 的 `currId` 不变 | 路由变了视图没跟上 |
| `[BR-DIAG]` 出现 host→child 洗掉 query | **桥接旧快照倒灌**（见第 4 节） |
| `isAuth: false` 且 `menuHasThird: false` | **三级权限缺失**（见 3.3） |

排查完务必移除埋点，并用 `diff` 确认与主应用版一致。

**读取嵌入模式权限**（`__POWERED_BY_WUJIE__` 只在子应用沙箱存在，宿主 console 取不到）：

```js
// 办法 A：DevTools Console 左上角切换执行上下文到 smart-technology，然后
const p = window.$wujie?.props?.platform;
console.log(p?.auth.getPermissions().filter((c) => c.startsWith('dexis:smartTechnology')));

// 办法 B：直接在宿主 console 读 localStorage（dev 模式不加密）
const k = Object.keys(localStorage).find((k) => k.includes('COMMON__LOCAL__KEY__'));
const perms = JSON.parse(localStorage.getItem(k).match(/"permissions":\s*(\[[^\]]*\])/)[1]);
console.log(perms.filter((c) => c.startsWith('dexis:smartTechnology')));
```

## 8. 给后续业务域迁移的提醒

1. **先确认业务域的导航层级数**。`DOMAIN_PAGES` 脚手架只适配「一组平级三级页」。超过一级的导航结构，应让页面自己拥有导航，外壳退化为纯容器 —— 不要为了套脚手架而压层级。
2. **迁移前先普查 URL 契约的消费方**。`grep` 所有读 `route.query` 的位置（面包屑、页签标题、页面名、分享链接、埋点 pageId）。这些消费方不在导航层，改路由形态不会同步，且失效时症状与路由 bug 难以区分。
3. **`platform.auth.onAuthChange` / `platform.fullscreen.onChange` 必须做内容比对**。它们底层是 `$subscribe`，触发频率远高于语义；直接赋值会造成引用抖动，进而击穿下游 `deep` watch 的状态。
4. **`auth.ready()` 在嵌入模式不等权限**。凡是依赖权限做鉴权/重定向的地方，都要区分「未就绪」与「无权限」，并为「落到 unauthorized 后权限才到」准备兜底。
5. **优先埋点，而非推断**。双向桥接 + 多层 query 的场景，纯代码推断成本高、易错。三点埋点法（见第 5 节）一次点击即可定位。
6. **`check-domain-scaffolds.mjs` 是字面量正则校验**，不是 AST 分析。改配置写法（引用常量、注释里出现同形字样）都可能让它误判。
