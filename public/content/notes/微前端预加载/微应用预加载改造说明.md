# 微应用预加载改造说明（modulepreload 方案）

- 涉及文件：`src/microfrontend/preload.ts`（唯一改动文件）
- 调用方：`src/main.ts` → `preloadBusinessApps()`
- 背景版本：wujie / wujie-vue3 `2.1.0`
- 前身提交：`a9eb7f517 feat(智能科技):预加载`

## 一、问题现象

主应用停留在经营驾驶舱首页一段时间后（`preloadApp` 早已执行完），再切到「智能科技」，仍然要等很久才能看到子应用首屏——预加载像是完全没生效。

生产构建和本地 `pnpm dev:mfe` 两个环境都能复现。

## 二、根因：wujie 不预取 `type="module"` 脚本

### 2.1 子应用入口是 ESM

子应用产物 `apps/smart-technology/dist/index.html`：

```html
<script
  type="module"
  crossorigin
  src="/micro-apps/smart-technology/assets/index-DdVb0qoK.js"
></script>
<link rel="stylesheet" crossorigin href="/micro-apps/smart-technology/assets/index-DC7ytx9u.css" />
```

其中 `index-*.js` 约 **1.5MB**，整个 `assets/` 目录 13MB。

### 2.2 wujie 对 module 脚本直接返回空串

`node_modules/.pnpm/wujie@2.1.0/node_modules/wujie/esm/entry.js:202-219`：

```js
// module should be requested in iframe
return scripts.map(function (script) {
  var src = script.src,
    async = script.async,
    defer = script.defer,
    module = script.module,
    ignore = script.ignore;
  var contentPromise = null;
  if ((async || defer) && src && !module) {
    // …fetchAssets
  } else if ((module && src) || ignore) {
    contentPromise = Promise.resolve(''); // ← module 脚本：不发任何请求
  }
  // …
});
```

注释已写明原因：ESM 必须由浏览器在 iframe 内**原生**加载，无法用 `fetch` 取回文本再注入执行（module 有自己的解析、依赖图和作用域语义）。所以 wujie 只把 `src` 记下来，等 `sandbox.start()` 时才 `scriptElement.setAttribute("src", …)` 交给 iframe 下载（`esm/iframe.js:878-881`）。

### 2.3 `exec: false` 的预加载因此等于空转

改造前的实现向 `WujieVue.preloadApp` 传了 `exec: false`。看 `esm/index.js:224-325` 的 `runPreload`：

```js
if (!exec) {
  // …
} else {
  await getExternalScripts(); // exec:false 走这里
}
```

对 module 脚本来说，`getExternalScripts()` 就是 `await Promise.resolve("")`——**零网络请求**。

预加载实际只拿到了两样东西：

| 资源          | 大小                         | 落入缓存         |
| ------------- | ---------------------------- | ---------------- |
| `index.html`  | ~500B（且线上是 `no-store`） | `embedHTMLCache` |
| `index-*.css` | 15KB                         | `styleCache`     |

真正的大头 1.5MB 入口 JS 一个字节都没预取，全部留到点击那一刻才开始下载。

### 2.4 更糟：旧预加载是负收益

`startApp` 在发现已存在 sandbox 且 `alive: false` 时（`esm/index.js:79-160`）：

```js
if (!sandbox.preload) { /* … */ }
await sandbox.preload;                        // ① 先等预加载 Promise 跑完

case 5:
  if (!isFunction(_iframeWindow.__WUJIE_MOUNT)) {  // ② exec:false ⇒ 脚本没跑过 ⇒ undefined
    _context2.next = 8; break;
  }
  // …快速重挂载分支（走不到）
case 8:
  return sandbox.destroy();                   // ③ 销毁，回到 case 9 从零重建
```

因为 `exec: false` 意味着子应用脚本从未执行，`iframeWindow.__WUJIE_MOUNT` 恒为 `undefined`，命中 `case 8` → `await sandbox.destroy()` → 全新建一个 sandbox。

于是旧方案的净效果是：

- 后台创建 3 个 iframe、渲染 3 份 shadow DOM 模板；
- 进入子应用时**先等这些预加载跑完，再全部销毁重来**；
- 换来一个 `no-store` 的 HTML 请求和 15KB CSS。

所以本次是**替换**而非叠加。

## 三、改造方案

在主应用空闲时，读取子应用入口 HTML，为其入口 module 脚本注入 `<link rel="modulepreload">`，把**浏览器 HTTP 缓存**焐热；iframe 之后请求同一批 URL 直接命中缓存。

不创建 sandbox、不执行子应用代码、不触发任何业务接口。

### 3.1 为什么 `modulepreload` 能解决问题

`modulepreload` 与普通 `preload` 的关键差别：浏览器不仅下载该模块，还会**解析它的静态 `import` 并递归预取整张同步模块图**。因此一条入口链接即可覆盖入口 JS 及其全部静态依赖，无需自己去解析 `import` 关系。

这也是 dev 环境同样能获益的原因——Vite 的 unbundled ESM 是几百个模块的静态 import 图，`modulepreload` 会一路铺开。

### 3.2 核心实现

```ts
// 只解析入口 HTML，不执行任何脚本：DOMParser 产出的文档是惰性的，不会加载子资源。
function parseEntryAssets(html: string, appUrl: string) {
  const document = new DOMParser().parseFromString(html, 'text/html');
  // …querySelectorAll('script[type="module"][src]') / link[rel="stylesheet"][href]
}

async function warmAppAssets(app: MicroBusinessAppDefinition) {
  const response = await fetch(app.url, { credentials: 'omit' });
  if (!response.ok) throw new Error(`入口响应 ${response.status}`);

  const { modules, styles } = parseEntryAssets(await response.text(), app.url);
  styles.forEach((target) => appendPreloadLink(target, 'preload', 'style'));
  modules.forEach((target) => appendPreloadLink(target, 'modulepreload'));
}
```

### 3.3 四个关键决策

**① CSS 用 `preload as="style"`，不用 `stylesheet`**

`rel="stylesheet"` 会把子应用样式**真正应用到主应用文档**上，造成全局样式污染。`preload as="style"` 只下载不生效。

**② module 脚本强制 `crossorigin`**

```ts
.map((target) => ({ ...target, crossorigin: true }))
```

ESM 按规范总是以 CORS 模式请求。预取与 iframe 内实际加载的 credentials mode **必须一致**，否则算两条不同的缓存条目，会重复下载一遍，预取白做。

已确认三个子应用的 dev server 均配置 `cors: true`（`apps/*/vite.config.ts`），生产同源。

**③ 三个子应用串行排队**

```ts
function warmNextApp(apps, index) {
  requestIdle(() => {
    void warmAppAssets(app)
      .catch(/* … */)
      .finally(() => warmNextApp(apps, index + 1));
  });
}
```

每个应用前都过一次 `requestIdleCallback`。若并发预取，三张模块图会一起抢带宽，反而拖慢主应用自身的路由懒加载分包。

**④ 单应用失败只告警，不中断**

`warmAppAssets` 的异常收敛为 `console.warn('[mfe preload skipped]', …)` 并继续下一个。预加载是纯优化路径，任何失败都不应影响主应用或后续子应用的正常加载。

### 3.4 开关与过滤

- `VITE_MFE_PRELOAD_ENABLED`（`.env.production:30`）：显式为 `'false'` 时关闭，未定义默认启用。语义与改造前一致。
- 智能科技受 `isSmartTechnologyMfeEnabled()` 二次过滤，与 `registry.ts` 的 `resolveBusinessApp` 保持同一判据。
- 模块级 `requested` 标志保证只跑一次；`injectedHrefs` 集合避免多个子应用共享同一 URL 时重复注入 link。

## 四、与部署缓存策略的配合

`docs/microfrontend/微前端部署目录与Nginx治理方案.md:114-121` 已为 `assets/` 配置长期缓存：

```nginx
location ^~ /micro-apps/commercial-society/assets/ {
    expires 1y;
    add_header Cache-Control "public, max-age=31536000, immutable" always;
}
```

带 hash 的 `assets/` 是 `immutable, max-age=1y` 且**同源**，预取结果能稳定命中，这是本方案在生产环境收益最大的前提。

入口 `index.html` 是 `no-store`，每次预加载都会重新拉取——这是刻意的，保证发版后拿到的是新的 hash 文件名，不会预取到已失效的旧资源。这一次请求仅约 500B。

## 五、验证方式

对着 **build 产物**验证（dev 环境收益小得多，见第六节）：

1. `pnpm build:mfe` 后经 nginx 访问主应用。
2. 打开经营驾驶舱首页，DevTools Network 中应在首屏加载完成后不久看到 `index-*.js` 的请求，Initiator 为 `modulepreload` / `(index)`。
3. 切到「智能科技」，同一个 `index-*.js` 请求的 Size 列应显示 `(memory cache)` 或 `(disk cache)`。
4. 观察三个子应用的预取请求是**依次**发起而非同时。

## 六、方案边界（明确不解决什么）

**省下的是下载时间，不是执行时间。** 本方案不覆盖：

- 1.5MB 入口 JS 的解析与执行；
- 子应用 Vue 应用初始化、`platform.auth.ready()`、首屏业务接口。

若焐热后进入仍明显卡顿，说明瓶颈在执行侧而非网络，需要另行评估 `exec: true` 的完整预执行方案。届时要一并解决预加载时 `props.platform` 缺失、导致子应用 `resolvePlatform()` fallback 到 standalone 模式自行取 token 的问题（`apps/*/src/platform/resolvePlatform.ts`）。

**dev 环境收益有限。** 预取的是 `/src/main.ts` 的模块图，但 Vite 的依赖预构建与按需编译本身就慢，且 dev server 不带长缓存头。dev 下仍偏慢属正常，不应据此判断改动无效。

**路由懒加载 chunk 不在覆盖范围。** `assets/` 里 13MB 的分包是动态 `import()`，`modulepreload` 的递归只跟随静态 import，这部分仍按需加载。
